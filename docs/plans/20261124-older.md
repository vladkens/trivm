# Older systems

`trivm create` for macOS 13, 14, 15 and 26 from their IPSWs, the Setup Assistant skipped by files the host writes to the guest's Data volume after the install, as Lima does, and for Ubuntu 22.04 with KDE Plasma, Debian 13 and Fedora 45, each with a desktop on X11. Done when each system is created on this Mac with no clicks, started, a command run in it and a shot of its desktop read, and wavo-app v0.3.0 installed and opened on the oldest macOS it supports (14: its DMG asks for 14.2) and on Debian, shots read.

## Decisions

- macOS: each version's last IPSW Apple published, from updates.cdn-apple.com: 13.6 (22G120), 14.6.1 (23G93), 15.6.1 (24G90), 26.6.2 (25G83); Apple published none for the security updates after them. Apple publishes no hash of these IPSWs (its IPSW catalog, mesu's `com_apple_macOSIPSW.xml`, lists only the current 27.2.1, with no digest): each is pinned by the SHA-256 of its download, which is ipsw.me's and, for 15 and 26, Lima's.
- Linux images, each a dated release pinned by SHA-256, checked against the distro's own sums:
  - `ubuntu-22.04`: Canonical's jammy cloud image of release-20261109 (`SHA256SUMS`).
  - `debian-13`: Debian's `generic` arm64 cloud image of 20261123-2671 (`SHA512SUMS`). Not `genericcloud`: its kernel, `linux-image-cloud-arm64`, is built without DRM, USB and HID (the kernel team's `config.cloud`), so it has no screen, keyboard or pointer on VZ; `generic` is the same cloud-init image with Debian's standard kernel.
  - `fedora-45`: Fedora Cloud Base Generic 45-1.4 from dl.fedoraproject.org, Fedora's own server rather than a mirror (`CHECKSUM`).
- All three qcow2 images compress their clusters with deflate (each header's compression type is 0), which the reader already handles: no zstd. The reader keeps refusing a zstd image with an error.
- `VZMacGuestProvisioningOptions` on 26, tried with a build that counted 26 as provisioned: VZ starts the VM with it and no error, and the guest ignores it, showing the Setup Assistant's hello and language screens two minutes on. The guest's side of it is new in 27, so 26 and older can't use it; 15, 14 and 13 weren't tried.
- The Setup Assistant, before 27: Lima's way (`pkg/guestpatch/macos`, Apache-2.0), without root. After the install, `diskutil image attach --noMount` attaches the disk, the Data volume (APFS role 0x40, found by its UUID in the container) is mounted by this user with `noowners`, and the files are written: `.AppleSetupDone`, `.skipbuddy` in the user template, the LaunchDaemon and its script. With `noowners` they land on the disk owned by 99:99; launchd loads only a daemon root owns, and `sudo` asks this Mac's password, so `src/apfs.rs` sets the owner to 0:0 in each file's inode on the detached disk: container superblock, object map, the volume's file-system tree from its root directory down by name, the inode record's owner and group rewritten and the node's Fletcher-64 checksum computed again, as Lima's `apfs_chown.go` does. It refuses an encrypted volume and a file owned by anyone else. `fsck_apfs -n` passes on the result.
- The script the LaunchDaemon runs as root, over two boots. The first: `sysadminctl -addUser` (admin), the home made, Lima's `com.apple.SetupAssistant.plist` in it so the first login's screens are marked seen, the automatic login, a restart. The second: Remote Login on, the daemon and script removed. Then the same key enrolment over SSH with the password and the same tuning as `macos-27`.
  - The automatic login is `/etc/kcpassword` written by the script (the password XORed with loginwindow's key, as `sysadminctl` writes it) and `autoLoginUser`: `sysadminctl -autologin set` fails at that point with `SACSetAutoLoginPassword error:22`, and loginwindow shows its password field.
  - The restart: loginwindow logs in by itself only at boot; restarting loginwindow showed the login window again. Remote Login waits for the second boot, so trivm's first SSH login doesn't race the restart.
- macOS 14 leaves its Data volume encrypted after the install (`fs_flags` 0x100, per-file keys, no `UNENCRYPTED`; `diskutil` shows it "FileVault: Yes (Locked)" before the first boot, its keys the guest's), and mounting it fails with "Illegal byte sequence": no file can reach it from the host without the guest, root or not, so Lima's way stops there. The brief's fallback: `create` sees the encrypted volume, says so, and boots into the Setup Assistant, which is answered by hand or by an agent with `shot`, `click`, `type` and `key` (the user `user`, the password `1234`, then Remote Login on in Terminal with `sudo launchctl load -w …/ssh.plist`); `create` waits up to 30 minutes for SSH, then enrols the key and tunes as for the others.
  - The automatic login moved into the tuning too (`/etc/kcpassword` and `autoLoginUser` over SSH), as the Setup Assistant leaves it off; it is the same login the first-boot script sets on 15 and 26.
- The IPSW's path is resolved before VZ loads it: through this lane's `cache` symlink VZ said "The restore image does not exist".
- Linux desktops, all on X11 so `DISPLAY=:0` over SSH reaches them, logged in automatically, sleep targets masked, the screen never blanked:
  - `ubuntu-22.04`: KDE Plasma from `kde-plasma-desktop` (Kubuntu's Plasma without its full application set, about a third of `kubuntu-desktop`'s download), SDDM autologin into the `plasma` X11 session, the screen locker and power management off in `/etc/xdg`.
  - `debian-13`: Debian's default desktop, GNOME, on X11 (`gnome-session-xsession`): GDM with `WaylandEnable=false` and automatic login, the idle, lock and suspend off in a dconf system database, GNOME's initial setup marked done. GNOME 48 still has its X11 session; the desktop task's extras (LibreOffice and the like) are left out.
    - GNOME Shell starts on its overview, where an app started over SSH stays a thumbnail without focus: an autostart entry closes it through the Shell's `OverviewActive` D-Bus property.
    - GNOME brings NetworkManager, which leaves the NIC to networkd as netplan says and reports no network, so apps asking it would think they're offline: netplan is given the NetworkManager renderer after the packages and applied, the same lease kept (the SSH session waiting on cloud-init survives it). Plasma here comes without NetworkManager and keeps networkd.
  - `fedora-45`: Fedora's Workstation is GNOME on Wayland only (GNOME 49 dropped X11), so Xfce (`@xfce-desktop`) with LightDM, as `ubuntu-24.04` has. Its Xfce adds xfce4-screensaver, which blanked and locked the screen after 5 minutes, and xfce4-power-manager: both off in system-wide xfconf defaults written after the packages.
  - `xdotool` on each, for `click`, `type` and `key`.
- cloud-init's wait runs as root: Fedora's `/run/cloud-init` is root's only, and `cloud-init status --wait` as the user never returned. Its exit code 2, done with recoverable errors (Fedora's hostname, set at a later try), counts as done.
- Disk: the 26 IPSW was deleted from the cache once 26 was proven, so that 14's download beside the `macos-15` VM kept the free disk above 60 GB; the 15 IPSW once 15 was proven. With the Mac's free disk near 55 GB from other work, the manager's rule from then on: each IPSW deleted as soon as its system is proven, each VM once proven, and no download or install that would leave less than 20 GB free. The raw disks converted from the Linux images of proven systems were deleted too (made again from the cached images on the next `create`).
