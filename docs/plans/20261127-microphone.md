# A microphone in the guest

An app's dictation is tested in a VM only with a microphone that hears something, and the Mac's own must stay out of it: no host microphone and no prompt on the host. `trivm mic <vm> <file>` plays an audio file from the host into a microphone of the guest's, on macOS, Linux and Windows, in real time, so an app recording from the default input hears it. `trivm mic <vm>` puts the microphone in the guest without playing anything, so it is there when the app starts. Done when, on this Mac, in a scratch VM of each system, a recording from the default input made while `mic` plays a test file holds that file's sound (its tones found in the recording on the host), and a shot of the system's sound settings shows the input device (shots read).

## Decisions

- The command: `mic <vm> [file]`, a top-level command beside `shot` and `type`, as the microphone is one more of the VM's inputs and works on all three systems; not under `os`. With a file, it returns once the file has played; sound no app records is lost, as a microphone's is. The microphone is put in the guest at the first use, as `ui` puts agent-desktop, so `mic <vm>` alone is how it is put there before an app starts.
- The file: any format macOS's `afconvert` reads (WAV, AIFF, CAF, MP3, AAC, FLAC), converted on the host to 16-bit mono PCM at 48 kHz, a microphone's format, the same for every system; trivm decodes nothing itself.
- Linux: the audio server's own virtual devices through `pactl`, whose PulseAudio protocol PipeWire's `pipewire-pulse` serves too: a null sink `trivm-mic-in` that the file is played into, and `trivm-mic`, a mono source remapped from its monitor, made the default input. The guest's own sounds go to a second, silent null sink `trivm-speaker`, the default output, so the microphone hears only the file: with `trivm-mic-in` the only sink, PulseAudio's `module-always-sink` would make it the default output. Loaded at once with `pactl` and kept for later logins in `/etc/pulse/default.pa.d` and `/etc/pipewire/pipewire-pulse.conf.d`, each server reading its own. Played by `pacat` from SSH's input, paced by the null sink's clock. Ubuntu 24.04's Xfce has PulseAudio 16.1 and `pactl`, its socket not yet started in the session that installed it: `mic` starts the server's socket.
- macOS: BlackHole 2ch 0.7.1 (Existential Audio, GPL-3.0), an AudioServerPlugIn, a driver coreaudiod loads with no kernel extension and SIP left as it is: its pkg from existential.audio, pinned by the SHA-256 that Homebrew's `blackhole-2ch` cask has (signed by Existential Audio's Developer ID and notarized), installed with `installer`; coreaudiod restarted, as its scripts don't. A VZ VM has no sound device, so BlackHole is the guest's only device, its default input and output, and `afplay` plays the file into it. No virtio-sound: VZ's only input source is the Mac's microphone (`VZHostAudioInputStreamSource`), which this item rules out, and its output would play the guest's sounds on the Mac. With BlackHole the only output, the guest's own sounds go to the microphone too. An app records only with TCC's microphone grant, which `os grant <vm> <app> microphone` writes.
- Windows: no virtual audio driver for arm64 with a fitting licence: VirtualDrivers' Virtual-Audio-Driver (MIT) is built for x64 only (its signed 25.7.14 has an x86-64 `.sys`), VB-Cable and Virtual Audio Cable are closed, Microsoft's SysVAD sample would have to be built and signed. So QEMU gives Windows a sound card, `ich9-intel-hda` with `hda-micro` (a speaker and a microphone), for Windows' own HD Audio driver, on QEMU's D-Bus audio backend (`-audiodev dbus`, which needs `-display dbus,p2p=yes`; VNC and QMP's screendump stay): nothing reaches the Mac's sound, and the speaker plays to no one. `mic` hands QEMU a socket for a D-Bus client (QMP's `getfd` and `add_client`), registers an `org.qemu.Display1.AudioInListener` on a second socket (`RegisterInListener`), and QEMU calls its `Read` for the microphone's samples, at the rate the guest records, which trivm answers from the file by the clock. The rest of the time the microphone is silent.
- D-Bus: the little of its wire protocol this needs, a small own routine in a file of its own, as `qcow2.rs`: the EXTERNAL authentication, messages with a unix fd, method calls, returns and errors, rather than `zbus` and an async runtime. QEMU's interface is read from its `ui/dbus-display1.xml` and `audio/dbusaudio.c` (11.1): QEMU authenticates the listener's connection as the server and calls `GetAll` on it, `Init`, `SetEnabled`, `Read`.
- Licences: BlackHole runs in the guest as a program of its own, a driver loaded by coreaudiod, downloaded from its author by the person's trivm at the first `mic`, as a distro's packages are; trivm hosts and links nothing of it. No code is taken from QEMU.

## Tasks

- [ ] 1. `mic <vm> [file]`: the command, `afconvert` on the host, `--help`, `readme.md`.
- [ ] 2. Linux: the virtual devices with `pactl`, kept for later logins, `pacat`.
- [ ] 3. macOS: BlackHole pinned, installed and loaded, `afplay`.
- [ ] 4. Windows: the sound card on QEMU's D-Bus audio, the D-Bus client, the listener fed from the file.
- [ ] 5. The proof on each system: a recording from the default input holding the file's tones, the sound settings' input in a shot.

## Checks

- `make check`, `make test`; unit tests for QEMU's command line, the D-Bus messages, the WAV read.
- On this Mac, in scratch VMs: `mic` on Ubuntu 24.04, macOS 27 and Windows 11, a recording of the default input checked on the host for the test file's tones, the sound settings in shots read; an app started before `mic` and after a restart still has the microphone.
