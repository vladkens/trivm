# macOS and Linux on Virtualization.framework

trivm's first version: an agent creates a macOS 27 or Ubuntu 24.04 VM with one command and no clicks, starts it in the background, runs commands and copies files over SSH, and sees and drives its screen from the host; the person opens a window onto it. Done when an agent installs wavo-app v0.3.0 in both and takes a screenshot of it, unattended.

## Decisions

- Commands: `create <system> [--name <vm>] [--cpus n] [--memory GiB] [--disk GiB]`, `start <vm>`, `stop <vm> [--force]`, `list`, `delete <vm>`, `ip <vm>`, `exec <vm> -- <cmd>`, `ssh <vm>`, `cp <src> <dst>` (`<vm>:<path>` on either side), `shot <vm> [file]`, `click <vm> <x> <y> [--right] [--double]`, `type <vm> <text>`, `key <vm> <keys>` (`cmd+space`, `enter`), `open <vm>`. A VM's name defaults to its system's. The arguments parsed by hand.
- Systems, each pinned by URL and SHA-256 in the code:
  - `macos-27`: Apple's IPSW of 27.2 (26B123).
  - `ubuntu-24.04`: Canonical's arm64 cloud image of a dated release, with Xfce on X11 (LightDM, logged in automatically) installed by cloud-init on the first boot. The image is qcow2, which VZ doesn't read: a reader of our own writes it as a sparse raw disk (`miniz_oxide` for its deflated clusters; the `.tar.gz` beside it holds only the root filesystem, with nothing to boot).
- Files, where Linux tools keep theirs, by the XDG Base Directory spec: `trivm` in `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME`, `$XDG_CACHE_HOME` and `$XDG_STATE_HOME`, or, when a variable is unset, empty or not an absolute path, in `~/.config`, `~/.local/share`, `~/.cache` and `~/.local/state`; each folder trivm makes, and those above it that are missing, its owner's only (0700), a VM's too.
  - Config, `<vm>.conf`: the VM's settings, `system`, `cpus`, `memory` and `disk`, as `key = value` lines; written once, when the VM is made, read at each start.
  - Data, `<vm>/`: `disk.img` (raw, sparse), the platform's files (macOS: `aux.img`, `hardware.bin`, `machine.bin`; Linux: `efi.bin`, `machine.bin`, `seed.iso` until the first boot is done), `mac`, the NIC's address, and `setup`, a mark while the first boot hasn't finished; trivm's SSH key, `id_ed25519`, beside the VMs' folders, made once under `id_ed25519.lock` and moved into place whole, the public half last, so `id_ed25519`, `id_ed25519.pub` and `id_ed25519.lock` aren't VM names, in any case.
  - Cache: downloads, kept, each written by one `create` at a time (a lock file beside it), the raw disks converted from them, and `entitlements.plist`.
  - State, `<vm>/`: `log`, `console.log`, `pid` (locked by the VM's process while it runs) and, while it runs, `ctl.sock`; made again when it is missing.
  - A VM's name is claimed by making its data folder, which fails if there is one; it shows once its config is written, before the install, so it lists as new while it installs. `delete` removes the data, the state, then the config.
- System tools only: `curl` (downloads, resumed), `shasum`, `ssh`, `scp`, `ssh-keygen`, `hdiutil makehybrid` (cloud-init's `cidata` ISO), `caffeinate`, `codesign`.
- A running VM is a process of its own: `start` runs `trivm _run <vm>` in a new session, its output to `log`, and waits for the desktop. It owns the VZVirtualMachine on the main thread of an accessory NSApplication (no Dock icon), keeps the Mac from idle sleep while the VM runs (`caffeinate -i -w <pid>`) and answers one request per connection on `ctl.sock`: `status`, `stop`, `kill`, `shot`, `lit`, `move`, `click`, `type`, `key`, `open`. It holds the lock on `pid` for its life, so a VM runs while the lock is held: a killed process's files or a reused pid don't count, and a second `_run` exits. The VM ends with the process; `stop` asks the guest to shut down, then stops it after a timeout.
- The display from the host, as Vitrine does it (VitrineVZ `DisplaySink.swift`, Apache-2.0): a VZVirtualMachineView in an opaque 4×4 borderless window at desktop level + 1, the view sized to the display in points; `shot` reads the IOSurface its layers show, made opaque (Linux's framebuffer is XRGB, its unused byte zero); clicks and keys are NSEvents sent to the view, which VZ hands to the guest's keyboard and pointer. A right click's event gets button 1 through its CGEvent: AppKit makes it with button 0, which VZ takes for a left click. `open` shows a normal window with the VM; closing it hides it again.
- Coordinates are a shot's pixels: macOS's display is 2× (3200×1800 pixels at 220 ppi), its shot is scaled to 1600×900; Ubuntu's is 1× (1920×1080).
- macOS: `VZMacOSInstaller` from the IPSW, then the first boot with `VZMacGuestProvisioningOptions` (macOS 27+, not in `objc2-virtualization` yet, declared by hand): the user `user`, password `1234`, logged in automatically, Remote Login on. trivm's key goes in by the first SSH login, the password given by trivm itself as `SSH_ASKPASS`. Then sleep, the screen saver and the screen lock off, the host's time zone.
- Ubuntu: the raw disk grown to its size (cloud-init grows the partition), EFI boot (`VZEFIBootLoader`), the seed with the user `user` (password `1234`, sudo without one, trivm's key), the desktop packages and autologin, the host's time zone, DHCP by the MAC address (networkd sends a DUID otherwise), SSH sessions on the desktop's display (sshd's `SetEnv DISPLAY=:0`); done when cloud-init reports done, then the seed goes (the desktop shows it as a disk). Its disk is cached by the host and synced with fsync, as Lima has it: with VZ's defaults ext4 lost files on the first boot.
- `start` returns when the desktop is up: its processes running (Dock, Finder; Xfce's session, panel and desktop), then the screen lit (macOS draws its desktop up to half a minute after the Dock starts).
- The guest's address from `/var/db/dhcpd_leases` by the MAC address kept in `mac` (VZ's NAT hands them out through bootpd).

## Result

Both systems install, start and are driven unattended on this Mac (macOS 27.2 host, Apple silicon):

- `create macos-27`: about 10 minutes to install from the cached IPSW, a few more for the first boot
  and the tuning; `start` returns with the desktop drawn in 20–30 s, `stop` takes about 10 s.
- `create ubuntu-24.04`: 80 s from the converted image to the Xfce desktop; `start` 9 s, `stop`
  2 s; `dpkg -V` clean after first boot, restart and a killed process.
- Shots, left and right clicks, typing, chords (`cmd+space`, `alt+f4`) checked with shots on both;
  `open` showed the window and shots kept working after it was closed.
- wavo-app v0.3.0 installed from its DMG and its `.deb` and opened, its window read in shots.
- Two `create`s of a name make one VM, two `start`s run one and both wait for it; a `pid` file left
  by a killed process, or naming another process, counts as stopped; a macOS setup cut short
  after the key went in finishes on the next `start` (24 s).

Found on the way: AppKit makes a right click's event with button 0, which VZ reads as left; Linux's
framebuffer reads as transparent; Ubuntu's DHCP lease is keyed by a DUID; ext4 on VZ's default disk
caching lost files on the first boot (the qcow2 reader was checked against an independent one).

Not checked: closing the `open` window with the host's mouse (no Accessibility permission here);
it was closed by `performClose` through a request added for the test and removed.
