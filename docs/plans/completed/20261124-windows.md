# Windows 11 on QEMU

`trivm create windows-11`: Windows 11's install media made from Microsoft's own arm64 download and installed unattended into a VM run by Homebrew's `qemu` with HVF and `swtpm`, driven by the same commands as the macOS and Linux VMs (start, stop, list, delete, ip, exec, cp, ssh, shot, click, type, key, open). Done when an agent installs Windows 11 with no clicks, runs a command, copies files both ways, drives the desktop and installs and opens wavo-app v0.3.0's Windows arm64 build, all checked on this Mac with shots read.

## Decisions

- The source: the ESD of Microsoft's Media Creation Tool, as Parallels and CrystalFetch get Windows, not the ISO of Microsoft's download page, whose flow refuses requests that don't come from a browser (`GetProductDownloadLinksBySku` answers `Sentinel marked this request as rejected` unless the page's device-fingerprint script ran). The tool's catalog, `https://go.microsoft.com/fwlink/?LinkId=2156292`, redirects to `Products-Win11-24H2-6B.cab` (29,467 bytes on 2026-11-25), whose `products.xml` (`bsdtar -xf`) lists 988 ARM64 ESDs on Microsoft's CDN, `dl.delivery.mp.microsoft.com`, each with its size and SHA-1. trivm pins the English consumer one, `26100.4349.250607-1500.ge_release_svc_refresh_CLIENTCONSUMER_RET_A64FRE_en-us.esd` (Windows 11 24H2, 4,527,171,158 bytes; the catalog lists it under each consumer edition with SHA-1 `c78fd344e845d3b17cb91c40bf4a856459da1b6c`, which the download matched), by its URL and SHA-256 `c01b6f47…`, in the system table, as the other systems are pinned; the catalog isn't read at run time. The CDN answers HTTPS with Fastly's fallback certificate, not one for its name, so the URL is HTTP; the SHA-256 checks the file.
- The media, made once and kept in the cache as `<esd>.pro.iso` (5.2 GB), the ESD then removed: with `wimlib-imagex` from Homebrew's `wimlib` (LGPL, a host tool beside `qemu` and `swtpm`, as CrystalFetch uses it; WIM's LZMS isn't a small routine), image 1's files (Setup's media), images 2 and 3 (Windows PE, Setup) exported into `sources/boot.wim`, 3 the one booted, and image 6, Windows 11 Pro (the ESD holds Home, Home Single Language and Pro as 4 to 6), into `sources/install.esd`, its solid LZMS blocks copied as they are (7 s; 4.36 GB). Then `hdiutil makehybrid` makes an ISO9660 and UDF image (UDF for `install.esd`, past ISO9660's and FAT32's 4 GiB a file) with an El Torito image for UEFI (platform 0xEF, no emulation, 3360 sectors), `efi/microsoft/boot/efisys_noprompt.bin`, which boots with no key to press. The ISO is what was tried first, and edk2 booted it; a FAT32 disk image would need `install.esd` split. `create` checks for `qemu-system-aarch64`, `swtpm` and `wimlib-imagex` before downloading.
- `--iso` goes: with the media made from the pinned ESD, a path to an ISO has nothing left to do, and the ISO it took was pinned to one file anyway.
- QEMU is the VM's process itself, no trivm process beside it: `start` starts `swtpm` (a daemon that ends when QEMU disconnects), then QEMU in a session of its own with the VM's locked `pid` file inherited, so the lock lives as long as QEMU, and writes QEMU's pid into it. trivm talks to QEMU over QMP on `qmp.sock`: `query-status`, `screendump` (PNG for shots, PPM to measure how lit the screen is), `input-send-event` (keys as QEMU's key codes, the pointer as the tablet's absolute axes, buttons), `system_powerdown`, `quit`, `device_del`, `set_password`, `query-vnc`.
- The machine: `virt` with `-accel hvf -cpu host`; edk2's `edk2-aarch64-code.fd` from QEMU's share folder and a copy of `edk2-arm-vars.fd` per VM (`efi.bin`); the system disk raw (`disk.img`, sparse) as NVMe, whose driver Windows has inbox; `ramfb` as the display, as Windows on arm64 has no virtio-gpu driver inbox (edk2's ramfb driver offers 640×480, 800×600 and 1024×768, no property sets more); `qemu-xhci` with `usb-kbd` and `usb-tablet`; `tpm-tis-device` on `swtpm`, with `ppi=off` (its physical-presence memory fails to map on HVF, `HV_BAD_ARGUMENT`; Windows' TPM check doesn't use it); the install media and the seed as USB CDs while the VM is set up, removed with `device_del` once it is, the disk with boot index 0 and the media 1 (edk2 connects only the devices QEMU gives a boot index, so a USB CD without one is never seen; a blank disk doesn't boot, so the media does, and once Setup has written Windows' boot files each of its restarts boots the disk); the RTC in local time, as Windows expects.
- The network: QEMU's user network, `virtio-net-pci` with the VM's MAC and a host port on 127.0.0.1 forwarded to the guest's 22, chosen free at each `start` and kept in the state folder's `port`; `ip` prints `127.0.0.1:<port>`, and `ssh`, `exec` and `cp` go through it (`scp://` URLs for `cp`). Its driver, NetKVM, comes from Fedora's virtio-win ISO 0.1.302 (pinned by SHA-256; the drivers are BSD-3-Clause), extracted with `tar` into the seed.
- SSH: Win32-OpenSSH's arm64 MSI 10.4.0.0 from its GitHub release (pinned by SHA-256, BSD licence), installed from the seed with trivm's key in `administrators_authorized_keys`. sshd's shell stays cmd; `exec` runs PowerShell 5.1, Windows' own, with the command line as `-EncodedCommand` (no quoting through cmd), UTF-8 output, no progress records, and exits with the last native command's code, or 1 when a cmdlet failed. `ssh` opens PowerShell too.
- The desktop from SSH: an SSH session has none, so an app started by `exec` would run unseen. `exec` and `ssh` define `desktop <program> [args]`, which registers a scheduled task run as `user` with the interactive logon type (it runs in the logged-on desktop session), starts it and removes it.
- The install: `autounattend.xml` on the seed (`seed.iso`, made by `hdiutil makehybrid`): en-US, the disk wiped (EFI, MSR, Windows), Windows 11 Pro with Microsoft's generic key for installing it (not activated), the TPM, Secure Boot and RAM checks skipped (`LabConfig`), `BypassNRO`, the local user `user` with password `1234` in Administrators, OOBE's pages hidden, one automatic logon whose first command runs `trivm-setup.ps1` from the seed: NetKVM, OpenSSH, the key, automatic logon for good, no sleep, screen-off, lock screen or automatic updates, sshd started last. Time zone: UTC (Windows names zones its own way; no table of them in trivm).
- `create` waits for SSH with the key (the install takes 11 minutes on this Mac), with no key pressed (the media's boot asks for none, and the disk boots first once it has Windows), removes the CDs, then waits for the desktop like `start`: `explorer.exe` running for `user`, then the screen lit.
- The files, on the XDG layout #1 brought: the settings in `~/.config/trivm/<vm>.conf`; the disk, the firmware's variables (`efi.bin`), the TPM's state (`tpm/`), `mac`, the `setup` mark and the seed while it is set up in `~/.local/share/trivm/<vm>/`; the downloads in `~/.cache/trivm`; QEMU's `log`, the `pid` lock, `qmp.sock`, the screen's dumps, swtpm's `tpm.sock`, `tpm.log` and `tpm.pid`, and `port` in `~/.local/state/trivm/<vm>/`.
- `stop`: `shutdown /s /t 0` over SSH, else `system_powerdown`, then QMP `quit`, then a kill. `open`: QEMU's VNC on 127.0.0.1 (first free display) with the password `1234`, handed to Screen Sharing by `open vnc://`.

## Result

Blocked on the ISO: Microsoft's download page gives the arm64 ISO only to a browser
(`GetProductDownloadLinksBySku` answers `Sentinel marked this request as rejected` without its
device-fingerprint script), so no Windows was installed and task 6 is not done. Everything up to the
ISO's own contents runs on this Mac (QEMU 11.1.3 from Homebrew, swtpm, Apple silicon):

- QEMU with the VM's command line on HVF, driven by trivm, on an Ubuntu disk in place of Windows:
  `start` in 14 s, `list`, `ip`, shots read, a click that opened a menu, `key ctrl+alt+t` and `type`
  into the terminal it opened, `exec` (exit codes, quoting, stdin) through PowerShell 7 named
  `powershell`, `cp` both ways, `ssh`, `open` (Screen Sharing connected with the password), `stop`
  (the guest's journal shows a clean power-off) and `start` again.
- `create windows-11` with a bootable stand-in for the ISO in a separate cache: the virtio-win and
  OpenSSH downloads checked by SHA-256, the seed built (`autounattend.xml` well-formed, the setup
  script, the key, OpenSSH's MSI, NetKVM's arm64 driver), swtpm and QEMU started with both CDs,
  the firmware booting the ISO's El Torito image first and trivm's Enter presses reaching it.
- Without `--iso`, `create` prints where to get the ISO; a file with another SHA-256 is refused.

Found on the way: a USB CD with no boot index is never connected by edk2 when the disk has one;
`tpm-tis-device`'s physical-presence memory fails on HVF; swtpm writes its errors only to its log;
QEMU's pid went into the lock file after its old contents; PowerShell's errors over SSH come as
CLIXML unless `-OutputFormat Text`; SSH's readiness probe ran `true`, which cmd hasn't (now
`exit 0`); `start` took the VM's lock only after starting swtpm; a stopped VM's saved port could reach
another VM (`ssh`, `exec`, `cp` and `ip` now need the VM running); OpenSSH's MSI starts sshd
itself (stopped again until the script's end); `query-vnc` lists its clients before the server.

Not checked, as they need Windows: Setup with the answer file, the first logon's script, `desktop`
through a scheduled task, `exec`'s PowerShell 5.1 (native arguments are quoted differently from 7),
Windows' screen size (ramfb offers up to 1024×768; Fedora's virtio-win has an arm64 display driver,
`viogpudo`, for more), wavo-app's arm64 setup. With the ISO: `trivm create windows-11 --iso <path>`.
