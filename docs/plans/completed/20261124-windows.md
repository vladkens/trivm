# Windows 11 on QEMU

`trivm create windows-11`: Windows 11's install media made from Microsoft's own arm64 download and installed unattended into a VM run by Homebrew's `qemu` with HVF and `swtpm`, driven by the same commands as the macOS and Linux VMs (start, stop, list, delete, ip, exec, cp, ssh, shot, click, type, key, open). Done when an agent installs Windows 11 with no clicks, runs a command, copies files both ways, drives the desktop and installs and opens wavo-app v0.3.0's Windows arm64 build, all checked on this Mac with shots read.

## Decisions

- The source: the ESD of Microsoft's Media Creation Tool, as Parallels and CrystalFetch get Windows, not the ISO of Microsoft's download page, whose flow refuses requests that don't come from a browser (`GetProductDownloadLinksBySku` answers `Sentinel marked this request as rejected` unless the page's device-fingerprint script ran). The tool's catalog, `https://go.microsoft.com/fwlink/?LinkId=2156292`, redirects to `Products-Win11-24H2-6B.cab` (29,467 bytes on 2026-11-25), whose `products.xml` (`bsdtar -xf`) lists 988 ARM64 ESDs on Microsoft's CDN, `dl.delivery.mp.microsoft.com`, each with its size and SHA-1. trivm pins the English consumer one, `26100.4349.250607-1500.ge_release_svc_refresh_CLIENTCONSUMER_RET_A64FRE_en-us.esd` (Windows 11 24H2, 4,527,171,158 bytes; the catalog lists it under each consumer edition with SHA-1 `c78fd344e845d3b17cb91c40bf4a856459da1b6c`, which the download matched), by its URL and SHA-256 `c01b6f47…`, in the system table, as the other systems are pinned; the catalog isn't read at run time. The CDN answers HTTPS with Fastly's fallback certificate, not one for its name, so the URL is HTTP; the SHA-256 checks the file.
- The media, made once and kept in the cache as `<esd>.pro.iso` (5.2 GB), the ESD then removed: with `wimlib-imagex` from Homebrew's `wimlib` (LGPL, a host tool beside `qemu` and `swtpm`, as CrystalFetch uses it; WIM's LZMS isn't a small routine), image 1's files (Setup's media), images 2 and 3 (Windows PE, Setup) exported into `sources/boot.wim`, 3 the one booted, and image 6, Windows 11 Pro (the ESD holds Home, Home Single Language and Pro as 4 to 6), into `sources/install.esd`, its solid LZMS blocks copied as they are (7 s; 4.36 GB). Then `hdiutil makehybrid` makes an ISO9660 and UDF image (UDF for `install.esd`, past ISO9660's and FAT32's 4 GiB a file) with an El Torito image for UEFI (platform 0xEF, no emulation, 3360 sectors), `efi/microsoft/boot/efisys_noprompt.bin`, which boots with no key to press. The ISO is what was tried first, and edk2 booted it; a FAT32 disk image would need `install.esd` split. `create` checks for `qemu-system-aarch64`, `swtpm` and `wimlib-imagex` before downloading.
- `--iso` goes: with the media made from the pinned ESD, a path to an ISO has nothing left to do, and the ISO it took was pinned to one file anyway.
- QEMU is the VM's process itself, no trivm process beside it: `start` starts `swtpm` (a daemon that ends when QEMU disconnects), then QEMU in a session of its own with the VM's locked `pid` file inherited, so the lock lives as long as QEMU, and writes QEMU's pid into it. trivm talks to QEMU over QMP on `qmp.sock`: `query-status`, `screendump` (PNG for shots, PPM to measure how lit the screen is), `input-send-event` (keys as QEMU's key codes, the pointer as the tablet's absolute axes, buttons), `system_powerdown`, `quit`, `device_del`, `set_password`, `query-vnc`.
- The machine: `virt` with `-accel hvf -cpu host`; edk2's `edk2-aarch64-code.fd` from QEMU's share folder and a copy of `edk2-arm-vars.fd` per VM (`efi.bin`); the system disk raw (`disk.img`, sparse) as NVMe, whose driver Windows has inbox; `ramfb` as the display, as Windows on arm64 has no virtio-gpu driver inbox (edk2's ramfb driver offers 640×480, 800×600 and 1024×768, no property sets more); `qemu-xhci` with `usb-kbd` and `usb-tablet`; `tpm-tis-device` on `swtpm`, with `ppi=off` (its physical-presence memory fails to map on HVF, `HV_BAD_ARGUMENT`; Windows' TPM check doesn't use it); the install media and the seed as USB CDs while the VM is set up, removed with `device_del` once it is, the disk with boot index 0 and the media 1 (edk2 connects only the devices QEMU gives a boot index, so a USB CD without one is never seen; a blank disk doesn't boot, so the media does, and once Setup has written Windows' boot files each of its restarts boots the disk); the RTC in UTC, which Windows reads as local time, its zone being UTC (with the RTC in the host's local time, Windows ran 2 hours ahead on this Mac until NTP set its clock).
- The network: QEMU's user network, `virtio-net-pci` with the VM's MAC and a host port on 127.0.0.1 forwarded to the guest's 22, chosen free at each `start` and kept in the state folder's `port`; `ip` prints `127.0.0.1:<port>`, and `ssh`, `exec` and `cp` go through it (`scp://` URLs for `cp`, the path escaped, as scp decodes `%` escapes and `+` as a space, and `\` as `/`, as Windows' sshd finds no path with `\`). Its driver, NetKVM, comes from Fedora's virtio-win ISO 0.1.302 (pinned by SHA-256; the drivers are BSD-3-Clause), extracted with `tar` into the seed.
- SSH: Win32-OpenSSH's arm64 MSI 10.4.0.0 from its GitHub release (pinned by SHA-256, BSD licence), installed from the seed with trivm's key in `administrators_authorized_keys`. sshd's shell stays cmd; `exec` runs PowerShell 5.1, Windows' own, with the command line as base64 of UTF-8 that `-Command` decodes and runs with `iex` (no quoting through cmd; `-EncodedCommand` writes errors as CLIXML when stderr isn't a console), its output through `Out-Default` before the `exit` (else `-Command` drops the tables it hasn't formatted yet), UTF-8, no progress records, and exits with the last native command's code, or 1 when a cmdlet failed or the script doesn't parse (a `return` keeps the last program's code). cmd runs lines of 8191 characters at most, so a script past about 4 KB is refused with a hint to copy it over and run it. PowerShell doesn't wait for a windowed program, a setup among them: `Start-Process -Wait`, as the readme has it. `ssh` opens PowerShell too.
- The desktop from SSH: an SSH session has none, so an app started by `exec` would run unseen. `exec` and `ssh` define `desktop <program> [args]`, which registers a scheduled task run as `user` with the interactive logon type (it runs in the logged-on desktop session), starts it, waits until it has started (a task removed before it starts never runs) and removes it; it fails when the program didn't start (the task's result, `0x80070002` for a missing one) or not within 10 s.
- The install: `autounattend.xml` on the seed (`seed.iso`, made by `hdiutil makehybrid`): en-US, the disk wiped (EFI, MSR, Windows), the VM's name as the computer name (15 characters at most, letters, digits and hyphens, `win-` before one of digits only, which Windows refuses), Windows 11 Pro with Microsoft's generic key for installing it (not activated), the TPM, Secure Boot and RAM checks skipped (`LabConfig`), `BypassNRO`, the local user `user` with password `1234` in Administrators, OOBE's pages hidden, one automatic logon whose first command runs `trivm-setup.ps1` from the seed: NetKVM, OpenSSH, the key, automatic logon for good, no sleep, screen-off, lock screen or automatic updates, sshd started last. Time zone: UTC (Windows names zones its own way; no table of them in trivm).
- `create` waits for SSH with the key (the install takes 11 to 15 minutes on this Mac), with no key pressed (the media's boot asks for none, and the disk boots first once it has Windows), removes the CDs, then waits for the desktop like `start`: `explorer.exe` running for `user` and `FirstLogonAnim.exe` gone (Windows 11's first sign-in animation, which covers the desktop for a minute and a half after explorer starts), then the screen lit.
- The files, on the XDG layout #1 brought: the settings in `~/.config/trivm/<vm>.conf`; the disk, the firmware's variables (`efi.bin`), the TPM's state (`tpm/`), `mac`, the `setup` mark and the seed while it is set up in `~/.local/share/trivm/<vm>/`; the downloads in `~/.cache/trivm`; QEMU's `log`, the `pid` lock, `qmp.sock`, the screen's dumps, swtpm's `tpm.sock`, `tpm.log` and `tpm.pid`, and `port` in `~/.local/state/trivm/<vm>/`. swtpm splits its options at commas with no escape, so a data or state folder with a comma in its path is refused.
- Clones (`clone` and `run`, from main): a Windows VM's data folder is cloned as the others' are (the disk, `efi.bin`, `tpm/`), with a MAC address of its own and no machine identifier, which a VM on QEMU hasn't; its computer name stays the original's.
- `stop`: `shutdown /s /t 0` over SSH, else `system_powerdown`, then QMP `quit`, then a kill; a VM that is starting is waited for until QMP answers, as its pid is trivm's until QEMU's replaces it. `open`: QEMU's VNC on 127.0.0.1 (first free display) with the password `1234`, handed to Screen Sharing by `open vnc://`.

## Result

Windows 11 installs with no clicks and no file from the person, all checked on this Mac (QEMU
11.1.3, swtpm 0.10.2 and wimlib 1.14.5 from Homebrew) in folders of its own, shots read:

- `trivm create windows-11`: the ESD downloaded (about 9 minutes at 8.4 MB/s; one cut short
  resumed) and checked, the media made in under a minute, Windows installed to its desktop,
  logged in, no key pressed: 15 minutes from the media (11½ on an earlier run). Windows 11 Pro
  10.0.26100.4349 ARM64, PowerShell 5.1, the screen 800×600.
- `exec`: `cmd /c ver`, a table, exit codes 7 and 4, 1 for a cmdlet's error and for a script that
  doesn't parse. `cp` both ways with `+`, `%`, a space and `é` in the names, a folder up. `ssh` in a
  terminal. `key win` opened Start, `type` searched it, a click opened Notepad, typed into.
  `open`: Screen Sharing connected to QEMU's VNC.
- wavo-app v0.3.0's arm64 setup run with `/S` (exit 0), Wavo opened by `desktop`, a click on its
  About tab. `stop` in 10 s, `start` to the desktop in 21 s. `run windows-11` with a script: the
  clone up, its exit code 5 passed on, the clone deleted, its file not in the original; 23 s.

Found on the way: Windows 11's first sign-in animation covers the desktop for a minute and a half
after Explorer starts; with the RTC in the host's local time Windows ran 2 hours ahead;
`-EncodedCommand` writes errors as CLIXML; `-Command` drops output it hasn't formatted at an `exit`;
a scheduled task removed before it starts never runs; PowerShell doesn't wait for a windowed setup;
a path past 104 bytes for the state folder's sockets fails, so a scratch run's state folder is short.

Left: an app `desktop` starts stays behind a window that has the focus (Windows' foreground lock);
Windows isn't activated; the screen is ramfb's (Fedora's virtio-win has `viogpudo`, an arm64
display driver, for more).
