# The XDG folders

trivm keeps its files where Linux tools keep theirs, by the XDG Base Directory spec, in place of one folder, `~/.trivm` (`TRIVM_HOME`): what a person sets in `~/.config/trivm`, each VM's disks and platform files in `~/.local/share/trivm`, downloads and what is made from them in `~/.cache/trivm`, what VMs and trivm write as they run in `~/.local/state/trivm`, each moved by its variable. Done when, on this Mac, with its VMs moved into the new folders by hand, `trivm list` shows them, `macos-27` starts, runs a command, is shot and stops, a `run` on `ubuntu-24.04` runs a command in its clone and shoots it, a new `debian-13` is created, runs a command, is shot and deleted (shots read), and each file is where this plan puts it.

## Decisions

- The folders: `trivm` in `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME`, `$XDG_CACHE_HOME` and `$XDG_STATE_HOME`, or, when a variable is unset, empty or not an absolute path (which the spec says to ignore), in `~/.config`, `~/.local/share`, `~/.cache` and `~/.local/state`. trivm makes each folder of its own, and those above it that are missing, for its owner only (0700), as the spec asks; a VM's folders too. Folders made before keep their mode, as before.
- `TRIVM_HOME` goes: a test or a scratch run sets the variables, the four or some of them, as one sharing the cache's downloads sets all but `XDG_CACHE_HOME`.
- Config, `<vm>.conf`: the person's settings for each VM, `system`, `cpus`, `memory` and `disk`, as `key = value` lines. One file per VM in one folder, not a folder holding one file: a person sees the VMs' settings in one `ls` and edits one. trivm writes it once, when the VM is made, and reads it at each start.
- Data, `<vm>/`: `disk.img`; the platform files (macOS: `aux.img`, `hardware.bin`, `machine.bin`; Linux: `efi.bin`, `machine.bin`; Windows: `efi.bin`, the TPM's state in `tpm/`); `seed.iso` until the first boot is done; and the machine's state that goes with its disk:
  - `mac`, the NIC's address, the machine's as `machine.bin` is its identifier: the guest's DHCP lease and address follow it, a clone gets its own, and a VM whose state folder is wiped keeps it.
  - `setup`, a mark while the first boot hasn't finished (the config's `setup = true` before), beside macOS 13 and 14's `assistant`: they say what the disk holds, so wiping the state folder can't make a VM half made look made.
  - trivm's SSH key, `id_ed25519` and `id_ed25519.pub`, beside the VMs' folders.
- Cache: the downloads (IPSWs, cloud images, virtio-win, OpenSSH, agent-desktop, the Windows ISO cloned from `--iso`), a `.part` while one downloads, the raw disks converted from the Linux images, and `entitlements.plist`, which trivm writes again each time it signs itself.
- State, `<vm>/`: `log`, `console.log`, `pid` (the VM's lock), `ctl.sock`, QEMU's `qmp.sock` and screen dumps, swtpm's `tpm.sock`, `tpm.log` and `tpm.pid`, and `port`, the host's port QEMU forwards to the guest's SSH: chosen free at each start and of no use once the VM stops, so a wiped state folder costs nothing but logs. A VM's state folder is made again when it is missing. trivm's other locks stay beside the files they keep, `<file>.lock`: the SSH key's in data, each cache file's in the cache, so runs with state folders of their own that share a cache share its locks too.
- Sockets: `~/.local/state/trivm/<vm>/ctl.sock` leaves 63 bytes for a name under macOS's 104 (`~/.trivm` left 75); `create` and `clone` refuse a longer name as before, with `qmp.sock` and `tpm.sock` as long as `ctl.sock`.
- Reserved names, in any case: `id_ed25519`, `id_ed25519.pub` and `id_ed25519.lock`, beside the VMs' folders in data. `cache` and `entitlements.plist` no longer share a folder with VMs, so they are names again.
- A VM's name is claimed by making its data folder, which fails if there is one: then its state folder and its machine's files are made, and it shows once its config is written, as a file written whole and hard-linked into place, which fails if there is one. `create` writes the config before the install, so the VM lists as new while it installs, as before; `clone` and `run` write it last, in place of the hidden folder renamed into place: a VM being cloned has no config, so nothing opens, starts or lists it. Of two creates or clones of a name one makes it, and the other is refused with the folder's path, as is a data folder left with no config (by hand, or by a kill); `run` takes the next name. `delete` removes the data, then the state, then the config: one cut short leaves a VM that `delete` finishes, never a disk with no config naming it; it removes nothing if the data folder's inode changed while it stopped the VM, as when another removed it and made one of its name. The reaper is told the inode of the clone's data folder, as it was told the hidden folder's, and `run`'s clone goes config, state, then that folder: a removal by `run` cut short, the reaper finishes.
- APFS clones: `clone` and `run` clone within the data folder, always one volume; on a volume that isn't APFS they fail as before ("clones need APFS"): a copy of a 64 GB disk isn't the second `run` is for. A Linux VM's disk from the cache, the Windows ISO from `--iso` and the firmware's variables from Homebrew's share are made with `cp -c`, which clones on one volume and copies otherwise (sparse on APFS; checked on a disk image here, as is that Rust's `fs::copy` writes the holes): the VM works either way, a copy only takes the space, so nothing changes there.
- No migration: trivm has no users yet. This Mac's files are moved by hand, renames on one volume: `macos-27` (SIP off, Wavo granted) and `ubuntu-24.04`, each config split into its `.conf` and `mac`, their logs and `pid` into state; the SSH key; the cache without its lock files; `~/.trivm-b`, an empty scratch home, deleted.
