# Throwaway clones

A test that needs a clean system each time gets one in seconds: `trivm run <vm> -- <cmd>` makes an APFS clone of a stopped VM, starts it, runs the command and deletes the clone, however the command ends; `trivm clone <vm> <name>` makes one to keep. Done when, on this Mac, a kept clone of `macos-27` runs beside the original, and a `run` on `macos-27` and on `ubuntu-24.04` touches a file in its clone and shoots it, the file absent from the original after, the time of each `run` measured.

## Decisions

- `run`'s command runs on the host, not in the guest, with the clone's name in `TRIVM_VM`: an app test needs `cp`, `exec`, `shot`, `click` and `key` on the clone, which only the host has; a command in the guest is `trivm exec "$TRIVM_VM" -- <cmd>` in it. One argument is a shell line (`sh -c`), more are run as they are, as `exec` has it. Its exit code is `run`'s (128 + the signal when a signal ended it).
- The clone goes on success, failure and Ctrl+C. While the command runs, `run` ignores SIGINT (the terminal sends it to the command too) and deletes the clone once the command exits. For a `run` that dies before (Ctrl+C while the clone starts, a kill), a reaper, `trivm _reap` in a session of its own started first, reads a pipe whose write end only `run` has: for each name `run` tries, it writes the inode of the clone's data folder (`~/.local/share/trivm/<name>`) and the name, once the folder is made and before any file is copied, then `done` once it has deleted the clone; at the end of the input, which comes when `run` ends however it ends, a last line that isn't `done` is a clone left. The reaper stops and deletes the VM of the name if its data folder has that inode, checked again under its lock (APFS doesn't reuse inodes, so a later clone of the name is left alone), by its folders alone, as a clone cut short in the making has no config yet: its config, its state folder, then its data folder last, so a removal cut short it finishes. `run` deletes its clone after the command the same way, so a command that deletes it and makes another of the name keeps that one.
- `run`'s clone of `<vm>` is `<vm>-run-<n>`, the lowest `n` free, its MAC address the original's with the last byte XORed with `n`: the same clone gets the same address each time, so a test suite run all day doesn't use up bootpd's pool of 253 addresses, whose leases last a day.
- `clone`: a random MAC address, as `create` makes; the clone isn't started. Both refuse a VM whose setup isn't done (its `setup` mark in the data folder) and a running one, and hold a shared lock on the original's `pid` (`~/.local/state/trivm/<vm>/pid`) while copying, which its process takes exclusive, so it can't start in the middle while clones made at once don't wait for each other. `delete` takes that lock exclusive after stopping the VM, so a VM being cloned isn't deleted; the reaper takes it as `delete` does, with no pid in it.
- A clone's name is claimed as `create` claims one, by making its data folder, `~/.local/share/trivm/<name>`, which fails if there is one; its state folder and `mac` follow, then its files, and its settings, `~/.config/trivm/<name>.conf`, last, written whole and hard-linked into place, which fails if there is one. Nothing opens, starts, lists or clones a VM with no config, so no one sees half a VM; of two clones of a name one makes it and the other is refused with the folder's path, as is a data folder left with no config, and `run` takes the next name past either. The clone is held, as `create` holds a VM, until its config is written, and while a failed one goes.
- The copy: `clonefile(2)` of each file and folder of the VM's data folder but `mac`, which the clone has its own of, so a 64 GB disk is cloned in milliseconds and its blocks are shared until written. Its settings are written anew to its own `.conf`, and the runs' files (`pid`, `log`, `console.log`, `ctl.sock`) are in the state folder, which isn't copied. The clone is made within the data folder, one volume: not on APFS, `clonefile` fails and so does the clone.
- A new machine identifier for each clone, as Apple asks of VMs running at once. macOS was checked both ways with the original and a clone running at once: with the original's identifier both guests had the same serial number and platform UUID and both worked; with a new one the clone booted to its desktop with a serial number of its own, its account, settings and SSH key as they were.
- Linux: Ubuntu's network config (cloud-init's netplan, kept once the seed is gone and cloud-init has disabled itself) matched the NIC by the MAC address the VM was made with, so a clone with another one would get no address: the seed now matches the virtio NIC by its driver, and `ubuntu-24.04` is made anew with it.
